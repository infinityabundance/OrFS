# OrFS vs an open-source WORM comparator, on the same machine

This document publishes a **same-machine, same-device, same-container-caps**
comparison between **OrFS (this Rust repository)** and **SeaweedFS 3.99**, driven
by one shared, bounded driver, plus a **plain-directory anchor** on the same
device. It is drawn from the machine-generated receipt

```
evidence/performance/oss-worm-compare.json
schema orfs.performance.oss-worm-compare.v1
```

and is regenerated by

```sh
sh scripts/container-oss-worm-compare.sh
```

Nothing here is a ranking. Two rows are comparable only at the same
`{workload, writers, readers, block_size}` and under the configuration
differences the receipt records; a local FUSE read, an internal transaction path,
and a distributed object store are **different interfaces**. Read the receipt's
`comparability` block — including `not_comparable` — before using any number.

## 1. What actually ran — and what did not

| arm | ran? | notes |
|---|---|---|
| **OrFS-Rust** | **yes** | mounted through the real FUSE path (the `orfs mount` code path, `fuse::spawn`) as a separate daemon process, `--direct-io --durability sync --backing-io sync`, group commit **off** |
| **SeaweedFS 3.99** | **yes** | staged from the pinned image `chrislusf/seaweedfs:3.99` (digest recorded), run as `weed server` (master + volume + filer on loopback) + `weed mount`, Go heap bounded (`GOGC=50 GOMEMLIMIT=700MiB`, recorded) |
| **ext4 plain-directory anchor** | **yes** (anchor, not a system) | the identical driver workload in a plain directory on the **same device**, with no FUSE and no WORM contract — it exists only so the device's own cost is visible |
| **OpenZFS retained snapshots** | **NO — SKIPPED** | see §7 |
| **Btrfs retained snapshots** | **NO — SKIPPED** | see §7 |

The workload is identical for every arm and driven by one shared driver function
that only ever sees a mount-point directory:

* **append**: a **4 096**-byte record written with `write(2)` followed by
  `fsync(2)` — **one durability barrier per record** — from 1 and 64 concurrent
  writers, each on its own file, for a bounded duration.
* **read**: uniform random `pread` at **4 KiB / 64 KiB / 1 MiB**, from 1 and 64
  concurrent readers, over a fixed **67 108 864**-byte file of deterministic
  content.
* Evidence volumes use an **8 388 608**-byte segment-size policy.

Every arm records `ops`, `bytes`, `ops_per_second`, `bytes_per_second`, mean /
p50 / p95 / p99 / p99.9 / max latency, `error_rate` / `errors`, and elapsed time,
plus an out-of-window byte-exact read-back check and an append byte cross-check.

## 2. Per-record durable appends (4 KiB + `fsync`)

One run, this host (see the honesty caveats in §8). `ops/s` is the arm's own
measured rate; `p50`/`p99` are per-operation `write+fsync` latencies.

| system | writers | ops | ops/s | p50 | p99 | is a real durability barrier? |
|---|---:|---:|---:|---:|---:|---|
| OrFS-Rust | 1 | 1 224 | 244.8 | 3.98 ms | 5.71 ms | **yes** (one `fsync` per record) |
| OrFS-Rust | 64 | 1 316 | 255.4 | 249.75 ms | 268.34 ms | **yes** |
| SeaweedFS 3.99 (`weed mount`) | 1 | 1 359 | 271.6 | 3.54 ms | 7.51 ms | **no** (see §5) |
| SeaweedFS 3.99 (`weed mount`) | 64 | 14 674 | 2 923.7 | 15.49 ms | 122.67 ms | **no** |
| ext4 plain directory (anchor) | 1 | 4 249 | 849.5 | 1.13 ms | 1.80 ms | yes |
| ext4 plain directory (anchor) | 64 | 18 977 | 3 764.0 | 3.56 ms | 63.11 ms | yes |

The device itself is the frame. The receipt records the device baseline
(`device_baseline.evidence_volume_device`): a bare 4 KiB `write(2)+fsync(2)` on
**the same device**, outside any mount, taken on a quiet device **before** the
workload runs. It is a single-run figure on a shared host and **moves materially
between runs** (a raw `fsync` stalls when the drive's write queue is saturated), so
read it as an order of magnitude — the receipt records it verbatim, and does not
curate it. The reasoning that uses it is scale-free:

The plain-directory anchor's 1-writer append (**849.5 ops/s**) is essentially
  *the barrier and nothing else* — a per-record durable append cannot be faster
  than its own barrier, and the anchor pays no FUSE and no commit bookkeeping;
* **OrFS-Rust at 1 writer is 244.8 ops/s (p50 3.98 ms) ≈ 3.5× the anchor's
  1-writer latency** — a real, measured cost of OrFS's FUSE request plus its
  commit path on top of the barrier (on this host's near-full ext4 drive).

### The loss, published as a loss

**OrFS-Rust's per-record durable append neither leads nor scales here.**

* At **1 writer**, OrFS-Rust (244.8 ops/s) is *slower* than SeaweedFS's FUSE
  client (271.6 ops/s) — a close race whose ordering flips between runs — but
  SeaweedFS's `Fsync` is **not** a stable-storage barrier (§5), so that row is
  **not** an equal-durability comparison and the receipt lists it under
  `not_comparable`.
* At **64 writers**, OrFS-Rust stays at **255.4 ops/s** — essentially the
  single-writer rate — while its `p50` explodes to **249.75 ms**. With group
  commit **off** (this court's equal-durability setting) every `sync` transaction
  takes its own barrier under the commit lock, so 64 writers queue behind one
  serialized commit path rather than overlapping. The **same device** in a plain
  directory reaches a few **thousand** ops/s with the same 64 native writers
  (3 764.0 in this run; 17 263.5 and 17 059.7 in the other runs of this phase —
  this arm moves a lot under host load), and SeaweedFS's barrier-free flush reaches
  2 923.7 ops/s. The ceiling at 64 writers is OrFS's commit serialization, **not**
  the device.

That is the honest result. The mechanism that removes this serialization — the
opt-in group-commit coordinator — is **deliberately OFF** in this court, because
amortising one barrier across many transactions is a *different durability
contract* and must never be presented as a per-record durable append (see §6).

|---:|---:|---:|---:|---:|---:|---:|---:|
| 4 KiB | 1 | 292 410.0 | 3.29 | 162 606.6 | 0.34 | 3 141 475.4 | 0.26 |
| 4 KiB | 64 | 1 605 360.0 | 29.12 | 3 165 487.0 | 0.46 | 25 705 310.5 | 0.25 |
| 64 KiB | 1 | 112 925.0 | 8.63 | 323 577.5 | 2.50 | 673 745.1 | 1.25 |
| 64 KiB | 64 | 821 019.9 | 56.83 | 1 840 886.8 | 3.20 | 4 418 205.9 | 1.76 |
| 1 MiB | 1 | 9 466.8 | 104.47 | 23 220.7 | 38.00 | 56 788.8 | 14.49 |
| 1 MiB | 64 | 23 175.2 | 2 502.36 | 59 678.2 | 105.94 | 162 287.5 | 41.54 |

The SeaweedFS 4 KiB read rows are **unstable between runs**: its in-process
client chunk cache holds a different amount of the file warm each time, and across
this phase's runs its 4 KiB rate moved by **more than an order of magnitude**
(1 reader: ~52 k → ~300 k ops/s). The rows above are the committed receipt's; they
are not a stable measurement, and no SeaweedFS 4 KiB comparison should be drawn
from them. OrFS's and the anchor's read rows are far more reproducible.

### The loss, published as a loss

**OrFS-Rust loses on large sequential reads, and loses badly.** At 1 MiB it does
**9 466.8 ops/s at 1 reader** against the plain-ext4 anchor's **56 788.8** and
SeaweedFS's **23 220.7**; at 64 readers it does **23 175.2** against **162 287.5**
and **59 678.2**. The 64-reader 1 MiB tail is worse still (`p99` 11.47 ms).

The small-block picture is more favourable and is *not* a clean win either: OrFS
stays competitive at 4 KiB (292 410.0 ops/s at 1 reader) and scales with readers,
but the comparison there is confounded by three different read paths — OrFS is
mounted with `--direct-io` and serves every read through the daemon from the
backing file's page cache; the anchor serves reads from the client's own page
cache; and `weed mount` serves warm reads from an **in-process chunk cache**, so
its sub-microsecond 4 KiB `p50` is a cache hit, not a backing read. The receipt
records this as `not_comparable` ("read-path caching shape") rather than pretending
the rows are the same operation.

## 4. Historical retention — the axis the reviewer asked for

A dedicated OrFS volume is driven through its mount for a bounded number of
**committed epochs** — one 4 KiB record plus `fsync(2)` each, so each epoch is one
committed transaction — and is then proved after unmount. OrFS retains **1 024**
epochs, giving **1 026** enumerated committed transaction boundaries; the proof is:

* every committed root is **enumerated** (`Log::boundaries`) and is a valid
  snapshot boundary;
* every committed root is **opened** as a historical view
  (`Snapshot::open_dir`) — **1 026** opened;
* every committed root is **enumerated** through its own root directory
  (`Snapshot::readdir`) — **1 026** enumerated;
* the epoch file is **read back byte-exact** at every root where it exists —
  **1 024** roots;
* **non-withdrawal** holds: the file only ever grows (it is a whole number of
  records at every root, never shorter than the earlier root's view, never longer
  than the final **4 194 304** bytes), so every earlier root is a byte-exact
  **prefix** of every later one;
* the same file's first bytes are byte-identical at every root (`read_at(ino, 0,
  16) == block_at(0, 16)` everywhere).

Measured costs (one run, this host):

| what | value |
|---|---|
| epoch commit (`write+fsync` through the mount), p50 | **3.99 ms** |
| historical-root access (open + enumerate + read back), p50 | **6.61 ms** |
| transaction count in the accounting | 1 025 |

**Space economics.** The receipt reuses the **existing** four-category storage
accounting (`Volume::storage_economics`, i.e. `orfs doctor --economics`) — no
second accounting is invented. For the retention volume, logical epoch bytes
4 194 304 produce **4 678 463** observed physical bytes, all in
`permanent_authoritative` plus 44 bytes of metadata (nothing in
`rebuildable_manifestation` or `temporary_construction`), an amplification of
**1.1154** — i.e. OrFS keeps every one of the 1 024 committed transitions for
about 11.5 % over the raw payload. The benchmark volume (the 64 MiB read file plus
both append arms) shows **1.0195** observed-over-logical.

**SeaweedFS on this axis: not comparable, and recorded as such.** `weed mount`
exposes **no** snapshot or historical-root interface, so there is nothing to drive
or measure. SeaweedFS's versioning lives in the Filer as a TTL-based,
metadata-level contract — a *different promise* from OrFS's non-withdrawal
authoritative log — so the receipt records the axis as `not_comparable` and
`measured: false` with that reason. It is not faked.

## 5. Why the interfaces differ (the honesty section)

The receipt's `comparability.differences` and `not_comparable` blocks are the
authority; in summary:

* **Durability is not equal.** OrFS-Rust takes **one `fsync` of its authoritative
  log per 4 KiB record**. SeaweedFS 3.99's FUSE client implements `Fsync` as a
  flush of the client's dirty pages to the co-located volume server plus a filer
  metadata commit over gRPC — with **no** `fsync` of the volume `.dat` file or the
  filer store. Its append rows are published, but they are **not** equal-durability
  with the OrFS rows and must not be read as such. `weed mount` is also **not
  SeaweedFS's fast path**.
* **The data path differs.** SeaweedFS is a client/server filesystem: even
  co-located, its data crosses the loopback network stack (HTTP) to the volume
  server and its metadata crosses gRPC to the filer, unlike OrFS's local
  in-process daemon.
* **The read caching shape differs** — see §3.
* **The mount knobs differ.** OrFS is mounted `--direct-io`; `weed mount` exposes
  no such knob. Recorded, not removed.
* **Group commit is off.** Every OrFS append row is a real per-record `fsync`
  through a real mount. The opt-in group-commit coordinator would amortise one
  barrier across a batch; **internal group-commit throughput is never a durable
  file append** and no row in this receipt is one (see §6).
* **The plain-ext4 anchor is not a WORM system.** It is the same driver workload
  on the same device with no FUSE and no WORM contract; it is a device/stack
  anchor only and is not ranked against the systems.

## 6. Group commit is not a durable append

Anywhere this project reports the **internal commit path** or the **group-commit
coordinator**, read it as a *mechanism* measurement, not as durable file appends:

* the in-crate commit-path microbenchmark (`docs/PERFORMANCE.md` §6, from
  `benches/mechanisms.rs`) measures the ordered commit path with **no `fsync` in
  the timed loop** — it is a throughput of the internal path, not a durability
  claim;
* the group-commit courts (`docs/PERFORMANCE.md` §10/§11, `docs/CONCURRENCY.md`
  §10) measure a coordinator amortising one barrier across a batch of *prepared
  transactions*; that is a different contract from one barrier per record;
* **this** court instead measures the equal-durability setting
  (`--durability sync`, group commit off) end to end through a real mount.

No document in this repository presents internal group-commit throughput as
durable file appends; where the numbers are quoted they are labelled as mechanism
or prepared-transaction figures, and this section makes the distinction explicit.

## 7. Probes: OpenZFS and Btrfs retained snapshots

The court **probes** both and records the concrete reason when they cannot run.
Neither ran here: **0** of the two probed filesystem-native snapshot arms ran.

| probe | ran | concrete reason recorded |
|---|---|---|
| **OpenZFS** | **no** | `/proc/filesystems` does not list `zfs`; `/sys/module/zfs` is absent; `zpool`, `zfs` and `modprobe` are all **not on `PATH`**; `modprobe` was not even attemptable. A plain container has neither the out-of-tree kernel module, nor the userspace, nor `CAP_SYS_MODULE`. (The sibling Go repository ran OpenZFS **inside a KVM micro-VM guest** with a real out-of-tree kernel module — a different environment.) |
| **Btrfs** | **no** | The host kernel **does** list `btrfs` in `/proc/filesystems`, but this court's container carries **no** `mkfs.btrfs` and **no** `btrfs` userspace and **no** loop device nodes (`/dev/loop-control` and `/dev/loop0` are absent; `losetup -f` fails). A btrfs filesystem cannot be created or mounted here, so no btrfs snapshot arm ran and none is implied. (The sibling Go repository ran Btrfs on a **loop-mounted 512 MiB image** in its container, where `mkfs.btrfs` and loop devices were available — so this is an environment limitation of *this* image, recorded as such, not a claim that Btrfs cannot be compared.) |

Both probes attempt the real operation (a bounded `modprobe zfs` / `losetup -f`)
and record its outcome, rather than asserting the conclusion.

## 9. Honesty caveats

1. These are **single-run** figures on one host under external load, with the
   evidence volumes on a near-full ext4 drive (the receipt records the exact
   backing filesystem and that device's own `write+fsync` cost, with a load
   caveat). Absolute values move between runs — the device baseline itself varies
   by an order of magnitude with load — so treat differences as noise unless they
   are large and structural.
2. **No ranking.** A row is comparable only at the same coordinate and under the
   listed differences. `SeaweedFS`'s append rows are **not** equal-durability;
   `weed mount` is not SeaweedFS's fast path.
3. The **losses are published as losses**: OrFS-Rust loses the 64-writer append
   scaling and the 1 MiB read throughput. The mechanisms behind both are named,
   not hidden.
4. **ZFS and Btrfs did not run.** No ZFS or Btrfs number appears anywhere in this
   document or the receipt.
5. The evidence volumes live on the **bind-mounted host drive**; the receipt
   records both that device's and the container's `TMPDIR`'s 4 KiB `write+fsync`
   cost so an absolute append number is always interpretable.
